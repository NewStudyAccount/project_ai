# 质量门验收清单

> 引入本方法论或评审现有文档体系时使用。逐项核对，输出「已达标 / 缺失 / 修复建议」差距报告。

## 一、契约层（L0）

- [ ] 有文档分工表，且每类文档声明了"不放什么"
- [ ] 有项目边界（明确不做 / Non-goals）清单
- [ ] 有「明确不引入」清单与反模式对照表
- [ ] 有待裁决事项唯一清单
- [ ] 目录结构为**具体目录树 + 模块职责表（放什么/不放什么）**，并声明目录纪律（AI 不得新建未登记目录），且与实际脚手架/代码一致
- [ ] 无版本号 / 端口 / 密钥 / 任务清单混入
- [ ] 入口文件（AGENTS.md 等）只做指针，未复制契约内容

## 二、设计层（L1）

- [ ] README 声明阅读顺序与效力顺序
- [ ] business-design 有状态机图 + 编号业务规则 + Non-goals
- [ ] table-design 有"结论清单先行" + 字段裁决说明（决策/取舍/原因）+ 开放问题唯一清单
- [ ] api-design 每接口具备八元组（接口名/方法/权限/幂等/入参/出参/逻辑/使用表）
- [ ] 接口逻辑含否定性约束（"不碰 X"）
- [ ] 通用能力以"裁剪取值"登记，未复制通用条文
- [ ] er-diagram.html 已从 table-design 派生生成；有前端边界的域 prototype.html 已生成并标注契约锚点
- [ ] 可视化效力低于正文，实装差异已登记

## 三、流程层

- [ ] SDD 入口可用（explore → propose → apply → archive）
- [ ] 变更归档后有文档偏差回写动作
- [ ] 阅读顺序写入规范（L0 → change 制品 → 代码）

## 四、AI 行为层（用实际交互验证）

- [ ] AI 修 bug 前会先索取报错/日志/traceId
- [ ] AI 对待裁决事项会停下来问
- [ ] AI 不顺手重构、不扩大改动范围

## 评审输出格式

```
## 差距报告：<项目/系统名>
### 已达标（N 项）
- [x] ...
### 缺失（M 项，按优先级排序）
- [ ] <缺失项> — 影响：<漂移/蔓延/决策丢失等风险> — 建议：<具体修复动作与落点>
### 修复优先级建议
P0（先做）：四核心机制补齐 —— ① 分工表 ② Non-goals + 反模式表 ③ 开放问题唯一清单 ④ 决策三元组
P1：骨架补齐（效力顺序、阅读顺序、八元组…）
P2：流程与 AI 行为层验证
```

## 适用边界（选择裁剪程度）

| 场景 | 用法 |
|---|---|
| 多系统单仓库 | 全套四层 + 每系统一个 docs/<system>/ 三件套 |
| 单体小项目 | L0 保留骨架 + L1 三件套可合并为一份设计文档，但分工表/唯一清单/裁决说明不可省 |
| 纯前端 / 纯脚本 | L0 的红线 + 反模式 + Non-goals 仍是核心；L1 可减为接口/数据两节 |
| 已有文档体系的团队 | 先补「分工表 + 唯一清单 + 裁决说明 + 效力顺序」四个机制，再逐步补齐骨架 |
