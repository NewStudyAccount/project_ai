# SDD 工作流闭环（规范驱动开发）

> L2 = 变更制品层，载体 `openspec/changes/<change-name>/`。写本次变更的提案/规格/设计/任务清单，单次变更 → 归档封存。不写通用编码教程。

## 流程总览

```
需求/缺陷
   │
   ▼
explore  ──► 读 L0 → 读相关 L1 → 现状调研（不写代码）
   │
   ▼
propose  ──► 生成变更：
   │           proposal.md（为什么做、边界）
   │           specs/（行为规格）
   │           design.md（技术设计）
   │           tasks.md（任务清单）
   │         ← 设计文档是"裁剪源"，变更提案从它裁剪，不反向污染
   ▼
apply    ──► 只按 tasks 清单落码；完成勾选状态位
   │         阅读顺序：L0 → 当前 change 制品 → 代码 → 枚举/Controller
   ▼
archive  ──► 归档封存；契约偏差回写 L1 文档
```

## 四条铁律

1. 代码实施**只按 tasks 清单**进行。
2. **不擅自修改** proposal / specs / design 定义（tasks 只允许勾状态位）。
3. 未归档前，该 change 制品是**唯一指令源**。
4. 落码后与设计有偏差：以代码 + specs 为准**回写设计文档**。

## 各阶段要点

### explore（调研）
- 只读不写代码。产出：现状认知、相关契约位置、影响面。
- 读 L0 契约 → 相关 L1 设计 → 现有代码与枚举/Controller（L3 真相）。

### propose（提案）
- proposal.md：为什么做、不做什么（边界）、影响范围。
- specs/：行为规格——对外可观察的行为变化。
- design.md：技术设计——从 L1 设计文档**裁剪**而来，不发明新口径。
- tasks.md：任务清单，每项可独立勾选完成；遇到待裁决事项必须先停下征询。

### apply（落码）
- 只做 tasks 清单上的事；完成一项勾一项。
- 不顺手重构、不"美化"、不扩大改动范围。
- 与设计冲突时：停下 → 确认真实契约（代码/Swagger 为准）→ 回写文档或征询。

### archive（归档）
- 归档封存 change 目录。
- 契约偏差回写 L1（设计文档与代码不一致处，以代码 + specs 为准改文档）。
- 检查 L0 待裁决清单是否需要更新。

## 与项目既有机制的关系

若项目已有 SDD 命令入口（如 `.claude/commands/opsx/`、`openspec/` 目录、openspec-* skills），**使用项目既有入口**，本流程只提供方法论约束（铁律、阅读顺序、裁剪方向），不重复建机制。
