# L0 契约层模板（CLAUDE.md 骨架与写作要领）

> L0 = 稳定契约层。跨变更稳定、全项目唯一事实源。入口文件（AGENTS.md 等）只做指针指向它。

## 定位

- **写**：技术栈、架构分层、工程规范、协作红线、反模式、待裁决事项
- **不写**：服务清单、业务词表、实现代码、依赖清单、生产密钥、版本号、端口、短期任务

## CLAUDE.md 骨架

```
# 项目全局规范
├─ 文档分工表          ← 每类文档的"写什么/不写什么"总表
├─ 1. 项目概述          ← 业务目标 + 项目边界（明确不做，防功能蔓延）
├─ 2. 技术栈            ← 唯一选型表 + 2.x「明确不引入」唯一清单
├─ 3. 环境配置与启动     ← 版本要求 + 启动/自检命令 + 配置管理约定
├─ 4. 目录结构（目标）   ← 多系统容器组织 + 脚手架落地顺序
├─ 5. 架构设计          ← 分层职责表 / 请求链路 / 模块边界 / 实体归属
├─ 6. 开发规范          ← 命名、接口、提交、错误码、DB、事务、安全、
│                        日志、性能、配置、横切能力（幂等/限流/重试）
├─ 7. 协作红线          ← AI 硬性要求（不可逆操作征询、不擅自改制品、
│                        不扩大改动、修 bug 必先看报错…）
│   └─ 7.1 反模式表     ← 「禁止做法 → 正确做法」对照表（唯一清单）
├─ 8. SDD 工作流        ← explore → propose → apply → archive
├─ 9. 待裁决事项        ← 悬空占位唯一清单（AI 遇到必须停下来问）
└─ 维护约定            ← 只保留稳定契约
```

## 写作要领

1. **边界（Non-goals）与正向需求同等重要**——AI 最容易在"没说不做的地方"发挥过度。项目概述必须含"明确不做"清单。
2. **反模式表用对照表而非段落**：左边是 AI 真实会犯的错，右边是一句话正确做法。示例：

   | 禁止做法 | 正确做法 |
   |---|---|
   | 凭推导实现接口/枚举 | 先确认真实契约（L3 代码/Swagger）再实现 |
   | 未看报错就批量改代码 | 先取报错/日志/traceId → 定位根因 → 最小修改 |
   | 同一事实写两处 | 只在唯一事实源写，其余位置放指针 |
   | 顺手"美化"重构 | 改动最小集，不加未要求的功能 |

3. **「明确不引入」独立成清单**：技术栈表说"用什么"，这份清单说"不许用什么"（如特定工具库、平行 UI 库…）。
4. **每条规范给出落点与唯一归属**（放哪个模块、谁负责），避免"都管一点"。
5. **目录结构必须具体且强制**：§4 要给出真实目录树 + 模块职责表（放什么/不放什么）+ 目录纪律（AI 不得新建未登记的目录）。**结构本身以脚手架/既有框架为准**，本文只负责把它钉死——模糊的"标准分层"表述等于没写，AI 一定会凭推导发明目录。
6. **指针机制**：AGENTS.md 等入口文件只写"指向 CLAUDE.md"，不复制任何内容——复制即漂移。

## L0 质量门自查

- [ ] 有文档分工表，且每类文档声明了"不放什么"
- [ ] 有项目边界（明确不做）清单
- [ ] 有「明确不引入」清单与反模式对照表
- [ ] 有待裁决事项唯一清单
- [ ] 无版本号 / 端口 / 密钥 / 任务清单混入
