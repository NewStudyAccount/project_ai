# 路线 B：开发业务功能（先设计 → 设计制品 → 按设计落码）

> 前置：路线 A 已完成（CLAUDE.md 存在且目录结构明确）。
> 产物：设计共识 → 三件套 + 原型图（有前端页面时）/ ER 图（有表变动时）→ 业务代码 → 偏差回写。
> 本路线**无 SDD 制品层**：三件套即唯一设计事实源，落码直接以它为准。

## Step 0：前置检查

- CLAUDE.md 存在、§目录结构明确？否则先走路线 A。
- 本次业务范围是否清晰？不清晰先向用户澄清，不得带雾开工。

## Step 1：设计前置（必做，不得跳过直接填模板）

**三件套是设计的表达，不是设计的发生地。**

1. **需求输入**（用户提供，AI 不推导补充）：业务目标、使用场景、边界与约束、非功能要求。
2. **AI 产出「设计要点提案」**（对话中的裁决材料，**不写任何文档**）：
   - 领域模型草案（主表/详细表怎么拆，拆分原因）
   - 状态机草案（状态、流转、编号规则）
   - 关键取舍清单（每条带「决策/取舍/原因」三元组）
   - **待裁决清单**（拿不准的逐条列出默认取值，等人拍板）
   - **变动判定**：是否存在数据库表变动？是否存在前端页面？（决定 Step 2 中 ER 图/原型图是否必做）
3. **用户逐条裁决**：确认 / 否决 / 修改。未裁决项不进文档；带默认值进的必须登记进开放问题清单。
4. **共识确认**：AI 复述最终设计要点，用户确认后进入 Step 2。

## Step 2：生成设计制品

复制 `assets/l1-starter/`（README / business-design / table-design / api-design）到 `docs/<domain>/`，按阅读顺序填充：business-design → table-design → api-design → 回填 README。**只写 Step 1 已裁决的内容**；填充中新出现的设计点回 Step 1 补裁决。

**填充要点**：

- business-design：Non-goals 对齐 CLAUDE.md；状态机 mermaid 图；业务规则逐条编号（R1、R2…）
- table-design：结论清单放最前；刻意取舍全部写进字段裁决说明；开放问题唯一清单
- api-design：每接口八元组（名/路径/权限/幂等/入参/出参/逻辑/使用表）；接口逻辑含否定性约束（"不碰 X"）；标注与基础模块的接线（权限点挂 RBAC、写操作挂操作日志注解）

**可视化生成条件表**：

| 产物 | 生成条件 | 依据与要求 |
|---|---|---|
| `er-diagram.html` | **存在数据库表变动（新增/修改表）时必做** | table-design 关系一览 + 表结构；mermaid erDiagram，标注主外键与基数 |
| `prototype.html` | **存在前端页面时必做**；纯后端功能省略 | business-design 路由树 + api-design 接口总表；页面元素标注契约锚点（接口 # / 规则 R 编号） |

省略时在 README 登记省略原因。可视化从正文派生，不一致时改图、查正文。

## Step 3：按设计落码

**阅读顺序：CLAUDE.md → 三件套 → 现有代码。**

1. **建库表**：按 table-design 建 SQL/迁移脚本（落点按 CLAUDE.md 约定），与字段裁决说明一致。
2. **写后端**：按 api-design 接口清单逐个实现——接口逻辑按编号步骤（校验 → 落库 → 审计 → 失败分支），否定性约束逐条遵守；写操作接上操作日志埋点，接口挂上 RBAC 权限点。
3. **写前端**：按 prototype.html 页面与契约锚点实现，路由/按钮权限接 RBAC，接口封装落点按 CLAUDE.md §目录结构。
4. **联调验证**：每个接口实现完即自测（含失败分支与错误码），最后整体联调。
5. **偏差纪律**：实现与设计冲突时**停下**；确属设计问题 → 回写三件套（并视情况更新 ER 图）再继续；属实现理解错 → 改代码。不得边写边悄悄改设计。

## Step 4：自检与收尾

跑 `references/self-check.md` 路线 B 清单，向用户交付：三件套 + 可视化 + 代码 + 联调结果 + 偏差回写说明。
