向量化 · 作用与原理

依据 knowledge-base-design.md §5.1/§5.2/§6.6 的设计落点 · 把"文本检索"升级为"语义距离检索"，弥补关键词检索对同义表述/模糊提问的失聪 · 项目使用 SiliconFlow bge-m3 生成 1024 维向量，存 ES dense_vector（cosine），与 BM25 关键词做 RRF 混合召回

实现步骤 优点 局限/差异 项目落点

作用：从「匹配字面」到「匹配意思」

检索方式机制示例（文档写"启动 node 进程"，你问"怎么把服务跑起来"）
关键词（BM25） 只找字面相同的词 问法里的"跑起来"与文档的"启动/运行"字面不一致 → 召回失败，死抠字面，同义/近义表达失聪
向量检索 先把文本编码成向量，再算语义距离 "部署/启动/运行/跑起来"在向量空间里挨得很近，虽字面不同也能被召回 → 召回率提升

1Embedding 模型：文本 → 长向量

用预训练模型（bge-m3）把一句话编码成串数字（1024 维），如 [0.32, -0.18, 0.77, …]。核心能力：语义近的文本向量近，语义远的向量远。向量即文本在"语义地图"上的坐标。

落地：EmbeddingProvider.embed(texts[])（§5.2）· 维度/模型存 ai_provider

2余弦相似度：算语义远近

两向量夹角的余弦，值域 [−1,1]，越接近 1 语义越近。这是向量相似度的标准度量。

落地：ES embedding 字段配 "similarity": "cosine"（§6.6）

3近邻搜索：找最接近的 K 个

把问题 q也用同一模型编码，再在向量库里找与 q 最近的 K 个片段（kNN / ANN）。用 HNSW 索引加速，不必全扫。

落地：ES knn 查询 + index_options: hnsw（§6.6）· 问答先把 q 向量化（§7.2）

4混合召回：语义 + 关键词互补

向量拾语义对、字面不对（同义/模糊）；BM25 拾字面精确（端口号/类名/配置键）。用 RRF 融合两路排名 → 语义+精确双优。

落地：knn + match(BM25) + RRF（§3/§6.6）· 这是选 ES 非纯向量的核心理由（§5.1）

核心公式：余弦相似度

cos(a, b) = (a·b) / (|a| · |b|)
代表两向量夹角的方向一致性，忽略长短。值 → 1 表示同向（语义近），值 → −1 表示反向，0 表示垂直无交。用于衡量两段文本语义上的接近程度，而不依赖字面是否重合。

直觉类比

传统关键词检索向量检索
比喻在书里 Ctrl+F 搜同样的字在语义地图上找意思接近的位置
失聪点打错字 / 换说法就找不到对精确专有名词（端口号/类名）区分偏弱，需 BM25 互补
结论精确术语强，语义弱语义强，精确弱

一句话总结作用：向量化把「文本检索」变成「语义空间的距离检索」，让机器能按意思而非字面召回内容，弥补关键词检索对同义表述 / 模糊提问失聪的短板；与 BM25 做 RRF 混合，则是对「语义」与「精确术语」的取长补短，正是项目选 ES 混合检索的动机。
  • 向量不落 MySQL：chunk 表只存业务字段（真相源），向量存在 ES knowledge_chunk_v1 的 dense_vector。
  • 同一模型约束：检索需与入库用同一 Embedding provider，切换 provider 须重建索引（§5.2）。
  • Embedding 不可用的降级边界：问题无法向量化 → 如实报错，语义检索无降级路径（§7.2）。
