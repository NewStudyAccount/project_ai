# AI 协作开发文档方法论（Doc-Driven AI Development）

> 提炼来源：`CLAUDE.md`（项目全局规范）+ `docs/blog-system/*`（blog 内容域设计文档集）
> 定位：把「如何为 AI 编码工具组织开发文档」沉淀为**可复用方法论**，文末附 Skill 封装草案
> 适用：任何由 AI 编码工具（Cursor / Claude Code / Trae / WorkBuddy 等）参与的工程项目

---

## 0. 一句话概括

**分层契约驱动**：把「稳定契约 / 领域设计 / 单次变更 / 代码真相」四层分离；每层只写自己的事，并**显式声明"不写什么"**；用**效力顺序**与**唯一清单**消灭双源漂移；用**红线 + 反模式表**约束 AI；让 AI 按 SDD（规范驱动开发）流程在明确护栏内落码。

---

## 1. 为什么需要这套方法（AI 时代的文档问题）

| 问题 | 症状 | 本方法的解法 |
|------|------|-------------|
| **双源漂移** | 同一事实在两处维护 → AI 不知信谁 → 输出不一致 | 单一事实源 + 指针文件 + 分工表 |
| **边界蔓延** | AI 顺手加功能、做"美化"重构 | 明确不做清单（Non-goals）+ 协作红线 |
| **决策丢失** | AI 把刻意取舍当"可优化项"改掉 | 字段裁决说明（决策/取舍/原因三元组） |
| **契约漂移** | 文档写一套、代码一套 | 效力顺序 + "代码与文档冲突以代码为准改文档" |
| **凭空实现** | AI 凭推导写接口/枚举，与真实契约不符 | 「先确认真实契约，不凭推导实现」红线 |
| **试错式修 bug** | 未看报错就批量改代码 | 修 Bug 硬性要求（先取报错→定位根因→最小修改） |

**核心认知：AI 把文档当规格说明书 + 护栏用。文档不是给人看的附属品，而是控制 AI 行为的主界面。**

## 2. 四层文档体系（金字塔）

```
        ┌─────────────────────────────────────┐
  L0    │  稳定契约层  CLAUDE.md               │  跨变更稳定、唯一事实源
        │  （AGENTS.md 只做指针指向它）          │
        └──────────────────┬──────────────────┘
                           ▼
        ┌─────────────────────────────────────┐
  L1    │  领域设计层  docs/<domain>/          │  业务语义、设计三件套
        │  business / table / api + 可视化      │
        └──────────────────┬──────────────────┘
                           ▼
        ┌─────────────────────────────────────┐
  L2    │  变更制品层  openspec/changes/<c>/   │  单次变更的指令源
        │  proposal / specs / design / tasks    │  （归档即封存）
        └──────────────────┬──────────────────┘
                           ▼
        ┌─────────────────────────────────────┐
  L3    │  代码真相层  枚举 / Controller /     │  字段级接口契约真相
        │  Swagger / 表结构                      │
        └─────────────────────────────────────┘
```

| 层 | 载体 | 写什么 | 生命周期 | 明确不写什么 |
|---|---|---|---|---|
| **L0 稳定契约** | `CLAUDE.md` | 技术栈、架构分层、工程规范、协作红线、反模式、待裁决 | 跨变更稳定 | 服务清单、业务词表、实现代码、依赖清单、生产密钥、版本号、端口、短期任务 |
| **L1 领域设计** | `docs/<domain>/` | 业务规则、状态机、库表契约、接口契约、原型 | 随业务演进 | 实现代码、生产密钥、端口账密、依赖版本、稳定契约口径（指针到 L0） |
| **L2 变更制品** | `openspec/changes/` | 本次变更的提案/规格/设计/任务清单 | 单次变更→归档 | 通用编码教程 |
| **L3 代码真相** | 枚举/Controller/Swagger | 字段级契约、真实取值 | 随代码 | ——（它本身就是真相） |

**配套指针机制**：`AGENTS.md` 等入口文件只写"指向 CLAUDE.md"，**不复制内容**——复制即漂移。

## 3. 六条元规则（方法论内核）

1. **单一事实源**：一件事只在一处定义；其余位置用指针引用（"唯一清单""唯一登记处""唯一裁剪源"是高频词）。
2. **显式分工表**：每个文档头部声明「本文放什么 / 不放什么」——**主动声明缺席内容**是防漂移的关键动作。
3. **效力顺序**：契约（L0）> 设计正文（L1）> 可视化原型（HTML/ER 图）。冲突时按序裁决，杜绝"原型即契约"。
4. **稳定 / 易变分离**：版本号、端口、账密、任务清单、完整实现永远不进契约层；契约只留"必须长成什么样"。
5. **决策留痕**：关键取舍写「决策 / 取舍 / 原因」三元组，防止后人（或 AI）把刻意设计当缺陷"修掉"。
6. **开放问题收口**：未决事项收敛到**唯一清单**，其他文档只指向它；AI 遇到清单内事项**必须停下来征询**，不得替业务做终裁。

## 4. L0 契约层写作模板（CLAUDE.md 骨架）

```
# 项目全局规范
├─ 文档分工表          ← 每类文档的"写什么/不写什么"总表
├─ 1. 项目概述          ← 业务目标 + 项目边界（明确不做，防功能蔓延）
├─ 2. 技术栈            ← 唯一选型表 + 2.2「明确不引入」唯一清单
├─ 3. 环境配置与启动     ← 版本要求 + 启动/自检命令 + 配置管理约定
├─ 4. 目录结构（目标）   ← 多系统容器组织 + 脚手架落地顺序
├─ 5. 架构设计          ← 分层职责表 / 请求链路 / 模块边界 / 实体归属
├─ 6. 开发规范          ← 命名、接口、提交、错误码、DB、事务、安全、
│                        日志、性能、配置、横切能力（幂等/限流/重试）
├─ 7. 协作红线          ← AI 硬性要求（不可逆操作征询、不擅自改制品、
│                        不扩大改动、修 bug 必先看报错…）
│   └─ 7.1 反模式表     ← 「禁止做法 → 正确做法」对照表（唯一清单）
├─ 8. SDD 工作流        ← explore → propose → apply → archive
├─ 9. 待裁决事项        ← 悬空占位唯一清单（AI 遇到必须停下来问）
└─ 维护约定            ← 只保留稳定契约
```

**写作要领：**
- 边界（Non-goals）与正向需求同等重要——AI 最容易在"没说不做的地方"发挥过度。
- 反模式表用**对照表**而非段落：左边是 AI 真实会犯的错，右边是一句话正确做法。
- 「明确不引入」独立成清单：技术栈表说"用什么"，这份清单说"不许用什么"（Hutool、Druid、平行 UI 库…）。
- 每条规范尽量给出**落点**（放哪个模块）与**唯一归属**（谁负责），避免"都管一点"。

## 5. L1 领域设计三件套模板

### 5.0 README（索引页）

必备元素：文档职责表（状态列）→ 实施状态 → **阅读顺序** → **效力顺序** → 范围一句话 → 裁剪取值登记 → 相关既有材料（指针表）。

### 5.1 business-design.md（业务逻辑总览）

| 章节 | 内容 | 要点 |
|---|---|---|
| 背景与边界 | 已知信息表（已知 → 本设计落点）+ Non-goals | Non-goals 对齐 L0，列出例外裁决 |
| 领域模型总览 | mermaid 图 + 主表/详细表拆分原因 | **拆分原因要写出来**（读多写少视角） |
| 状态机与业务规则 | 状态码表 + mermaid 状态图 + 编号规则 | 规则逐条编号，便于任务引用 |
| 库表设计 | 摘要 + 指针到 table-design | 明示"冲突以 table-design 为准" |
| 接口契约 | 摘要表 + 关键 DTO 字段 | 详细展开放 api-design |
| 前端边界 | 端职责表 + 信息架构（路由树） | 管理端/用户端分开 |
| 横切与安全 | 接线表（能力 → 本域怎么接） | **只接线、不改口径** |
| 架构落点 | 模块归属图（哪个模块放什么） | 实施时的硬约束 |
| 部署与迁移 | SQL 位置、种子、回滚 | |
| 文档分工 | 本文放什么/不放什么 | 元规则落地 |

### 5.2 table-design.md（库表契约）

| 章节 | 内容 | 要点 |
|---|---|---|
| **结论清单（先看这个）** | 既有表改不改 / 新增哪几张 / 待裁决点 | **结论先行**，读者 30 秒抓住全貌 |
| 通用原则的系统取值登记 | 对通用设计文档只登记"取值与差异" | **不复制通用条文**（裁剪源模式） |
| 表结构 | 字段/类型/空/默认/说明 + 索引 + 应用层约束 | 审计字段、发号、id 对外 String 等口径引用 L0 |
| 关系一览 | 文字版 ER | 详图放 er-diagram.html |
| **字段裁决说明** | 决策 / 取舍 / 原因 三列表 | **防"优化"**的核心机制 |
| 种子与迁移 | SQL 落点、种子数据 | |
| **开放问题（唯一清单）** | 编号 + 问题 + 默认取值 | 其他文档只指向本节 |

### 5.3 api-design.md（接口契约）

| 章节 | 内容 | 要点 |
|---|---|---|
| 全局约定 | 前缀/返回体/分页/id 类型/失败语义/幂等/时间格式 | 全部对齐 L0 口径，不复述细节 |
| 错误码语义 | 场景 → 语义枚举名 | 号段分配指针到登记处 |
| 按资源分节 | **接口名 / 方法路径 / 权限 / 幂等 / 入参 / 出参 / 接口逻辑 / 使用表** | 八元组是接口文档的最小完备结构 |
| 接口总表 | # | 方法 | 路径 | 权限 | 主要表 | 一览核对 |
| 典型调用顺序 | 新建/编辑等场景的调用链 | 帮助 AI 理解接口组合关系 |
| 文档分工 | 本文放什么/不放什么 | |

**接口逻辑的写法**：编号步骤，含校验 → 落库 → 审计 → 失败分支（错误码），并显式标注"**不**碰什么"（如"不改 content_file_id"）——否定性约束对 AI 极其重要。

### 5.4 可视化（低效力层）

- `er-diagram.html`、`prototype.html`：浏览器打开，仅作展示与交互参照。
- **原型标注契约锚点**（页面元素 → 对应接口/规则），但效力低于正文。
- 实装与原型的差异要在 README 登记（如"hero 统计条未实现，属可选装饰"）。

## 6. 关键机制详解

### 6.1 分工表机制（防双源漂移的第一道闸）

每个文档头部（或尾部）放一张两列表：

```
| 本文放什么 | 不放什么 |
|------------|----------|
| 业务规则、状态机 | 实现代码、完整枚举表 |
| 库表形态、接口语义 | 生产密钥、端口账密 |
| | 依赖版本（查 version-baseline） |
| | 稳定契约口径（查 CLAUDE.md） |
```

**"不放什么"里写清"该去哪查"**——把读者导航到唯一事实源。

### 6.2 唯一清单机制

以下内容全项目各存一份、别处只放指针：

- 「明确不引入」组件清单
- 反模式清单
- 待裁决事项清单
- 开放问题清单
- 错误码固定码值登记处
- 端口登记处 / 版本基线 / 测试环境账密

### 6.3 裁剪源模式（通用 → 系统取值）

当一份设计跨系统通用（如对象存储策略）：

```
通用设计文档（object-storage-design.md）
  = 唯一裁剪源：通用策略、封装、生命周期、安全红线

系统文档（blog README 的「裁剪取值」表）
  = 只登记「本系统取值 + 相对默认的差异」，不复制通用条文
```

**收益**：通用条文改一处全系统生效；系统文档保持轻量且差异一目了然。

### 6.4 裁决说明机制（防"优化式破坏"）

```
| 决策 | 取舍 | 原因 |
|------|------|------|
| 主表/详细表拆分 | 拆 | 列表不碰正文元数据；OSS 只存全文 |
| 正文进 OSS 不进 DB | OSS | 大字段拖垮列表与备份 |
| view_count 预留 | 预留 | 本期不做统计；避免后续加列 |
```

没有这张表，AI（和新同事）会把「预留字段」「故意冗余」「刻意拆表」当瑕疵清理掉。

### 6.5 红线 + 反模式表机制

- **红线**（协作纪律）：不可逆操作先征询、不擅自改制品定义、不加未要求的功能、改动最小集、修 bug 先看报错。
- **反模式表**（技术纪律）：把 AI 真实会犯的错列成对照表，每条一句话给正确做法。
- **待裁决清单**（业务纪律）：AI 遇到必须停下来问，不得替业务拍板。

### 6.6 接口级契约技巧

- **寻址约定**：`{idOrSlug}` 先按 id 精确匹配、再按 slug 唯一匹配、皆无按不存在——把歧义消解规则写进契约。
- **出参语义分端**：同一资源管理端返回源文、公开端返回渲染 HTML——显式标注两端字段语义差异。
- **否定性约束**："不改 X""不碰 Y""忽略 Z"要逐条写明。

## 7. AI 协作工作流（SDD 闭环）

```
需求/缺陷
   │
   ▼
/explore  ──► 读 L0 → 读相关 L1 → 现状调研（不写代码）
   │
   ▼
/propose  ──► 生成变更：proposal.md（为什么做、边界）
              specs/（行为规格）design.md（技术设计）tasks.md（任务清单）
   │         ← 设计文档是"裁剪源"，变更提案从它裁剪，不反向污染
   ▼
/apply    ──► 只按 tasks 清单落码；完成勾选状态位
              阅读顺序：L0 → 当前 change 制品 → 代码 → 枚举/Controller
   │
   ▼
/archive  ──► 归档封存；契约偏差回写 L1 文档
```

**铁律**：
1. 代码实施**只按 tasks 清单**进行。
2. **不擅自修改** proposal / specs / design 定义（tasks 只允许勾状态位）。
3. 未归档前，该 change 制品是**唯一指令源**。
4. 落码后与设计有偏差：以代码 + specs 为准**回写设计文档**。

# 文档驱动开发（Doc-Driven AI Development）

## 核心原则（必须遵守）
1. 单一事实源：一件事只写一处，其余指针引用
2. 每个文档声明「写什么 / 不写什么」
3. 效力顺序：稳定契约 > 设计正文 > 可视化原型
4. 稳定契约不写版本号/端口/密钥/任务清单/实现代码
5. 关键取舍写「决策/取舍/原因」三元组
6. 未决事项收口唯一清单；AI 遇到必须停下来征询

## 工作流程
### Step 1：搭 L0 契约层（CLAUDE.md）
按骨架产出：文档分工表 → 项目边界 → 技术栈+不引入清单 → 环境 →
目录结构 → 架构 → 开发规范 → 协作红线 → 反模式表 → SDD → 待裁决清单。
入口文件（AGENTS.md 等）只写指针。

### Step 2：写 L1 领域设计三件套（docs/<domain>/）
- README：职责表/实施状态/阅读顺序/效力顺序/范围一句话/裁剪取值
- business-design：背景与边界(Non-goals) → 领域模型 → 状态机与编号规则 →
  表摘要(指针) → 接口摘要 → 前端边界 → 横切接线 → 架构落点 → 部署 → 文档分工
- table-design：结论清单先行 → 裁剪取值 → 表结构(字段/索引/约束) →
  关系一览 → 字段裁决说明 → 种子迁移 → 开放问题唯一清单
- api-design：全局约定 → 错误码语义 → 按资源的接口八元组 →
  接口总表 → 典型调用顺序
- 可视化（ER 图/原型 HTML）效力低于正文，差异要登记

### Step 3：走 SDD 落码
explore → propose（proposal/specs/design/tasks）→ apply（只按 tasks，勾状态位）
→ archive（偏差回写设计文档）。不擅自改 proposal/specs/design。

## 10. 适用边界与变体

| 场景 | 用法 |
|------|------|
| 多系统单仓库（本项目形态） | 全套四层 + 每系统一个 docs/<system>/ 三件套 |
| 单体小项目 | L0 保留骨架 + L1 三件套可合并为一份设计文档，但分工表/唯一清单/裁决说明不可省 |
| 纯前端 / 纯脚本 | L0 的红线 + 反模式 + Non-goals 仍是核心；L1 可减为接口/数据两节 |
| 已有文档体系的团队 | 先补「分工表 + 唯一清单 + 裁决说明 + 效力顺序」四个机制，再逐步补齐骨架 |

**最小可行版本（4 件事）**：① 分工表 ② Non-goals + 反模式表 ③ 开放问题唯一清单 ④ 决策三元组。做到这四点，AI 输出的一致性即可显著提升。
