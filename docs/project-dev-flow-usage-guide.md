# project-dev-flow Skill 使用规范（搭项目 / 做业务操作手册）

> 适用 skill：`.workbuddy/skills/project-dev-flow/`（项目级）
> 定位：干活视角的双路线工作流——路线 A 搭项目、路线 B 做业务。**无 SDD 制品层，三件套即唯一设计事实源。**
> 配套：方法论深究查 `doc-driven-dev` skill；本文只讲怎么用。

---

## 一、路线判定（开口前先想清楚要哪条）

| 你要做的事 | 路线 | 触发口令示例 |
|---|---|---|
| 从零起一个新项目 / 生成 CLAUDE.md / 搭 RBAC 等基础内容 | **路线 A** | 「用 project-dev-flow 帮我搭一个新项目」 |
| 在已有项目里开发某个业务功能 / 业务域 | **路线 B** | 「用 project-dev-flow 开发 XX 功能」 |
| 项目还没初始化就想写业务 | 被打回路线 A | ——（skill 会自动前置检查） |

**一句话判断**：这个项目有没有跑通过的 CLAUDE.md 和基础骨架？没有 → 路线 A；有 → 路线 B。

---

## 二、路线 A：搭项目（初始化 + 基础内容）

### 流程五步

1. **信息收集**（AI 会问，不会编）：项目名、业务目标与边界、前后端技术栈、目录结构约定、数据库/中间件、部署形态。
   - 目录结构：你有既定样式就直接给（照抄你的框架习惯）；没有则 AI 按技术栈惯例提案目录树，**你确认后才生效**。
2. **生成 CLAUDE.md**：核心四件必填——① 项目概述（项目名/业务目标/明确不做）② 技术栈 ③ 目录结构（前端、后端各一棵树 + 职责表 + 目录纪律）④ 开发规范。红线、反模式等扩展节可标记后补（会登记待补清单）。
3. **基础内容询价**（先问再做，别跳过）：AI 出示默认清单，你逐项定「做 / 不做 / 改造」——
   - **默认必做**：RBAC 框架、登录日志、操作日志
   - **条件选做**：统一认证中心——仅当多系统统一登录 / token 互认 / 需对接第三方 IdP 时才做，AI 会先问三个判定问题再让你选型（自建 JWT / 对接 OAuth2 / 不做）
   - 每个模块的待确认口径（超管数据隔离、日志保留期限、脱敏字段）会在这一并问掉
4. **搭建与验证**：目录树 → 基础配置 → 公共占位（返回体/异常处理/启动入口）→ 按锁定清单搭模块（依赖顺序：RBAC → 登录日志 → 操作日志 → 认证中心）→ 启动/构建/联调验证。
5. **自检交付**：AI 跑路线 A 自检清单，交付 CLAUDE.md + 骨架说明 + 基础模块验证结果。

### 你的参与点（人必须出手的时刻）

- **目录树确认**——这是整个项目的硬约束，AI 后面不许建未登记目录，确认前多花两分钟看一眼
- **基础内容逐项拍板**——特别是认证中心：单系统项目默认不做，别被默认清单裹挟
- **模块口径拍板**——日志保留多久、哪些字段脱敏、超管能不能看全部数据

### 铁律（AI 遵守，你也可以拿来验收）

- CLAUDE.md 未生成前不搭任何目录
- 目录只认 CLAUDE.md §3，发现不合理先回写文档再创建
- 基础内容清单未经你确认不开工

## 三、路线 B：做业务（先设计 → 设计制品 → 按设计落码）

### 流程四步

1. **设计前置**（必做，AI 不得跳过）：
   - 你给需求输入（目标、场景、边界、约束）——AI 不推导补充
   - AI 出「设计要点提案」：领域模型草案、状态机草案、关键取舍（决策/取舍/原因）、待裁决清单，**此时不写任何文档**
   - 你逐条裁决 → AI 复述共识 → 你确认
2. **生成设计制品**：三件套（business-design / table-design / api-design）落到 `docs/<domain>/`，只写已裁决内容。两个可视化按条件生成：
   - **ER 图**：有数据库表变动（新增/修改表）→ 必做；无变动 → 省略并登记原因
   - **原型图**：有前端页面 → 必做（页面元素标契约锚点）；纯后端 → 省略并登记原因
3. **按设计落码**（无 SDD，直接干）：
   - 阅读顺序：CLAUDE.md → 三件套 → 现有代码
   - 按 table-design 建表、按 api-design 逐接口实现（含失败分支与错误码）、按 business-design 的 R 编号写业务规则
   - **接线别忘了**：接口挂 RBAC 权限点，写操作挂操作日志埋点
4. **自检交付**：跑路线 B 自检清单，交付三件套 + 可视化 + 代码 + 联调结果 + 偏差回写说明。

### 你的参与点

- **设计裁决**——提案里的每一条都值得看，特别是「待裁决清单」里 AI 给了默认取值的项
- **省略判定复核**——AI 说"无表变动所以不做 ER 图"，扫一眼 table-design 结论清单核实
- **偏差处理**——实现和设计打架时 AI 会停下问你，这是特性不是故障

### 铁律

- 三件套是设计的表达，不是设计的发生地——先裁决后落文档
- 落码只做三件套内的内容，不加功能、不顺手重构、不建未登记目录
- 设计冲突停下回写，不边写边悄悄改设计

## 四、常用口令速查表

| 你说 | AI 走 |
|---|---|
| 「用 project-dev-flow 搭一个新项目：<一句话业务>」 | 路线 A 全流程 |
| 「项目技术栈是 XX，目录结构按这个来：<粘贴样式>」 | 路线 A Step 1 信息补充 |
| 「基础内容就做 RBAC 和操作日志，认证中心不做」 | 路线 A Step 3 锁定清单 |
| 「用 project-dev-flow 开发 XX 功能：<需求描述>」 | 路线 B Step 1 设计前置 |
| 「设计要点第 2、5 条通过，第 3 条改成 XX，其余待定」 | 路线 B Step 1 裁决 |
| 「设计确认了，开始落码」 | 路线 B Step 3 |
| 「评审一下这个项目/功能的文档齐不齐」 | 对应路线自检清单，输出差距报告 |

## 五、两 skill 分工（别用混了）

| | project-dev-flow（本 skill） | doc-driven-dev |
|---|---|---|
| 定位 | 干活流程：搭项目、做业务 | 方法论参考：四层体系、六条元规则、机制详解 |
| 什么时候用 | 90% 的日常开发 | 想理解"为什么这么规定"、或评审/重构文档体系时 |
| 冲突时 | 以本 skill 流程为准 | 提供原理支撑 |

## 六、验收清单（快速版）

**路线 A 交付时看**：CLAUDE.md 核心四件齐且无空话 → 前后端两棵目录树具体到文件级职责 → 基础模块联调通过 → 认证中心"做/不做"有明确结论。

**路线 B 交付时看**：设计提案裁决记录在案 → 三件套 + 条件可视化齐 → 代码与三件套对得上（表/接口/R 规则抽查）→ RBAC 与操作日志接线在 → 无设计外功能。
