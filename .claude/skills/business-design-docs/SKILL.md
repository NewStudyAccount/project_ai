# 为业务域产出完整设计产物集（L1 领域设计）

面向多系统/多域仓库的业务设计文档产出流程。**范例（唯一样板）：本仓库业务设计产物集（路径见 `references/project-bindings.md` §5）**——动笔前先读它。

> 方法论正文：项目文档方法论（载体见 `references/project-bindings.md` §1），本 skill 是其 **L1 领域设计层**的执行流程与门禁。
> **分工铁律：事实裁决写在设计文档本身；流程与门禁在本 skill；章节骨架在 `assets/templates/`；项目耦合（文件名/路径/口径节号/工具约定）只在 `references/project-bindings.md`。四者不要互相抄。**
> **项目绑定层：** 本文与 references 其它文件只用**泛称**（「L0 契约文件」「错误码登记处」…）；泛称对应的本项目具体载体**唯一清单**见 `references/project-bindings.md`。移植新项目只改该文件 + 其 §8 清单列明处，主流程不动。

## 0. 先认清四层里本产物集站哪

| 层 | 内容 | 本 skill 管不管 |
|----|------|----------------|
| L0 稳定契约 | 项目契约文件（本项目载体见 project-bindings §1） | **不管**——只指针引用其口径，禁止复制条文（双源漂移） |
| **L1 领域设计** | **`docs/<domain>-design/`（本 skill 产物集）** | **管**：业务语义、库表契约、接口契约、可视化 |
| L2 变更制品 | 变更提案制品目录（project-bindings §1） | **不管**——设计定稿后经用户明确指示才走提案流程，禁止自作主张建提案 |
| L3 代码真相 | 枚举 / Controller / 表结构 | 不管——设计阶段只对齐既有真实契约，不凭推导编造 |

**效力顺序（写进每份产物）：** L0 契约 > `table-design.md` / `api-design.md`（字段级契约） > 主设计正文 > HTML（ER/原型/数据流，仅展示参照）。

**阅读顺序（写进 README）：** 主设计 → table-design → api-design → ER 图 → 原型。

## 1. 产物集全景（一单目录 = 一次业务设计的完整产物）

| # | 文件 | 职责 | 效力 | 必备性 | 范例文件 |
|---|------|------|------|--------|---------|
| 1 | `README.md` | 索引：文档职责表(状态)、范围一句话、阅读/效力顺序、裁决摘要、相关材料指针 | 索引 | **必备** | README.md |
| 2 | `<domain>-design.md` | 主设计：背景/边界、现状盘点、数据流、领域模型、选型对比、库表草案、接口草案、实施切期、开放问题、裁决记录 | 正文 | **必备** | knowledge-base-design.md |
| 3 | `table-design.md` | 库表契约：结论清单先行、DDL、索引/检索索引、种子、裁决记录、执行约定 | 字段级契约 | **必备**（有落库时） | table-design.md |
| 4 | `api-design.md` | 接口契约：全局约定、错误码段位、接口八元组、SSE 等特殊帧契约、权限/菜单对照 | 字段级契约 | **必备**（有接口时） | api-design.md |
| 5 | `<domain>-er-diagram.html` | 表关系 ER 图（浏览器打开） | 低（展示） | **必备**（有表时） | knowledge-er-diagram.html |
| 6 | `<domain>-prototype.html` | 页面原型（tab 切换多页面，标注契约锚点） | 低（交互参照） | **必备**（有界面时） | knowledge-prototype.html |
| 7 | `<domain>-dataflow.html` | 全链路数据流图（按阶段泳道） | 低（展示） | 可选（链路复杂时） | knowledge-dataflow.html |
| 8 | `<domain>-<topic>.html` | 科普/说明材料 | **非契约** | 可选 | knowledge-vector.html |

- **跳过「必备」产物（含条件必备）须经用户确认**，并在 README 与交付回话登记原因；AI 不得以「建议」「装饰」「新业务无范例」为由自行省略。
- 范例文件的完整路径与逐节对照见 `references/exemplar-map.md`（项目绑定内容）+ `references/project-bindings.md` §5。
- 目录命名：`docs/<domain>-design/`（kebab-case；与目录约定见 project-bindings §3）；主设计与目录同名。
- 状态标记（README 职责表状态列 + 各文档头部）：**探索稿 vN.N**（有开放问题）→ **设计稿**（开放问题清零、字段级契约落定）→ 实装后按变更回写。
- 裁剪源模式：跨域通用策略只登记**本域取值与差异**，不复制通用条文。

## 2. 判定走哪条路

| 用户诉求 | 走法 |
|---|---|
| 新业务域/新系统从零设计 | §3 全流程（八步） |
| 只补某几件产物（如“出个 ER 图”） | 只走对应步骤；产物齐了回写 README 职责表与状态 |
| 修订既有设计（裁决推翻/加表/加接口） | Step 1 裁决 → 只改相关文档 → 各文档「裁决记录 / 变更记录」登记 + **连带修正清单** |
| 只评审/挑毛病 | 按 `references/quality-gate.md` 检查并报告，**不直接改**；用户确认后再改 |
| “设计好了，开始写代码” | **不自作主张建变更提案**；提示用户走提案流程（须明确指示），并告知设计文档是字段级契约源 |
| 只是聊想法、还没到出文档 | 走探索模式或直接对话，不落产物 |

## 3. 执行流程（八步，每步有产物）

### Step 0 — 材料盘点与输入契约（缺就停下问，禁止编造）

先读：L0 契约文件全文（project-bindings §1）→ 相关既有材料 → 范例产物集。然后逐项收齐：

| 输入 | 取证来源 | 拿不到怎么办 |
|------|---------|-------------|
| 域名/目录名/主设计名 | 用户给定；kebab-case | 停下问 |
| 业务范围与目标用户 | 用户口述 + 既有系统现状 | 列「待补清单」交回 |
| 所属系统、落哪个库 | 既有系统目录与库（project-bindings §3） | 停下问 |
| 复用资产（表/SDK/横切能力） | 既有设计文档与代码 | 不确定就标注「待核实」，不凭推导 |
| 是否引入新组件/新选型 | 对照 L0 技术栈清单 + 不引入清单 | **新选型先经用户裁决并在 L0 技术栈登记后**才写进设计 |
| 新错误码段位 | 错误码登记处（project-bindings §2） | 未分配的先登记再写 api-design |
| 新端口/新组件版本/新账密 | 端口登记处 / 版本基线 / 账密登记处（project-bindings §2） | 设计里只指针，不写具体值 |
| 权限体系/菜单短号 | RBAC 短号规范 + 各系统既有种子（project-bindings §2） | 短号续号避撞（范例教训：撞号→种子静默失败） |

### Step 1 — 裁决收口（先裁决、后成文；禁止边写边拍板）

1. 把开放问题整理为编号清单 **Q1…Qn**（问题 + 倾向 + 默认取值）。
2. **分批与用户裁决**；未裁决项保持「开放问题」状态，**AI 不得替业务拍板**（L0 协作红线）。
3. 每项裁决记「**决策 / 取舍 / 原因**」三元组 + **回写落点**（哪些章节/文档要连带改）。
4. 裁决推翻先前内容时，登记**连带修正清单**。

机制细节见 `references/decision-mechanism.md`。

### Step 2 — 主设计 `<domain>-design.md`

按 `references/artifact-set.md` §2 骨架成文：背景与目标(分期目标 + **Non-goals**) → 现状盘点(可复用资产表) → 总体数据流 → 领域模型 + 状态机 → 关键选型对比(决策记录) → 库表草案(指针) → 接口草案(指针) → 实施切期 → 开放问题清单 → 裁决记录。
库表/接口在此只写**草案与摘要**，字段级契约让位 table-design / api-design（冲突以它们为准，文中明示）。

### Step 3 — `table-design.md`

结论清单先行（既有表改不改 / 新增哪几张 / 落点）→ 逐表 DDL（审计/发号/外键等口径指针 L0 数据规范，见 project-bindings §1）→ 检索索引定义（如有）→ 种子清单（RBAC 菜单/按钮短号、引导默认）→ **与主设计的偏差/裁决记录** → 执行约定（顺序、可重复执行、不可逆操作征询）。

### Step 4 — `api-design.md`

全局约定表（对齐 L0 接口/基础契约口径，指针不复述）→ 本域错误码段位（**先查错误码登记处防撞号**）→ 状态枚举透出值 → 按资源的接口**八元组**（接口名/方法路径/权限/幂等/入参/出参/接口逻辑/使用表）→ 特殊帧契约（如 SSE）→ 权限位与菜单对照 → 错误码明细 → 效力与变更 + 变更记录。
接口逻辑用编号步骤（校验→落库→审计→失败分支），并写**否定性约束**（“不碰 X”）。

### Step 5 — 可视化 HTML（低效力层）

**硬门禁：全量流程必须产出 ER 图（有表时）与页面原型（有界面时）**——业务全新、项目无范例也一样：规范壳在 `assets/templates/*.html.tmpl`，**不依赖范例**（范例只提升完成度）。数据流图与科普件才可选；ER/原型「不适用」仅限**无表 / 无界面**，其余跳过须经用户确认。

从 `assets/templates/*.html.tmpl` 起步；范例 HTML 存在时可参照它手写提升完成度：

- 全部**单文件自包含**（内联 CSS/JS，浏览器直接打开），页脚声明「效力低于设计正文」。
- 原型视觉 token 取**唯一取值处**（project-bindings §2 视觉 token；复制子集并注释出处）；原型 tab = 页面清单，元素上**标注契约锚点**（对应接口/规则）。
- ER 图与 table-design **同步**（表数、字段、关系一致）；数据流图与主设计 §3 同步。
- 科普/说明类 HTML 明确标注**非契约**。

### Step 6 — `README.md` 索引定稿

文档职责表（含状态列）→ **范围一句话** → 阅读顺序 → 效力顺序 → 状态与裁决摘要（批次 + 清零情况）→ 相关既有材料指针表。

### Step 7 — 质量门 + 交付

按 `references/quality-gate.md`（含跨文档自洽性检查）逐项过；按 `assets/acceptance-checklist.md` 验收；**自洽性 ERROR 清零**才算完。交付回话按 §4 格式。

> 起新目录可先跑模板实例化：`powershell -NoProfile -File .claude/skills/business-design-docs/scripts/new-domain-design.ps1 -Domain <domain> -DomainCn "<中文名>"`（可选 `-System` / `-Database`，详见 `references/artifact-set.md` §1）。

## 4. 交付回话格式（照此汇报，别只贴文件清单）

```
业务设计：<domain>（docs/<domain>-design/，状态：探索稿 vN.N | 设计稿）
产物：    README / 主设计 / table-design / api-design / ER / 原型 / 数据流 / 科普
          （逐项 列出；「不适用」= 条件不成立（无表→ER、无界面→原型）或经用户确认并登记原因；
           ER/原型「未做」= 交付不合格，须补做）
裁决：    Q1…Qn 共 m 项——已裁决 x / 未裁决 y（未裁决项列出编号+一句话）
质量门：  通过 a/b；未过项与原因
自洽性：  表数/枚举/错误码/菜单短号/权限位跨文档一致（是|否，差异清单）
登记：    错误码段位/端口/版本/账密（已登记 | 不涉及 | 待登记清单）
下一步：  （如：走变更提案——须用户明确指示）
```

## 5. 禁止清单（踩了就是错）

- **替业务拍板**：开放问题/待裁决事项未获用户裁决就写成定稿。
- **省略必备产物**：有表/有界面却不出 ER/原型，或未经用户确认把「必备/条件必备」标「不适用」（HTML 不是装饰，是产物集成员）。
- 把 L0 契约条文、通用设计条文**抄进**设计文档（指针引用；裁剪源模式只登记取值差异）。
- **凭推导编造**接口/枚举/错误码/字段（先查真实契约与登记处；查不到标「待核实」）。
- 错误码段位不经错误码登记处分配就写；跨系统撞号。
- 生产密钥/账密写进任何产物（测试账密只按 L0 安全规范与账密登记处）。
- **效力倒挂**：拿原型/HTML 当契约；主设计与 table/api-design 冲突时不登记偏差。
- 未获明确指示**创建变更提案**或改变更制品定义。
- 修订设计时顺手重构、扩大改动范围、隐式改契约（改动须在「裁决记录/变更记录」可追溯）。
- 多份产物间表数、状态枚举、权限位、菜单短号、错误码**不一致**（见 `references/quality-gate.md` 自洽性检查）。
- 同一事实写进两份产物各自维护（唯一清单只存一份，其余指针）。
